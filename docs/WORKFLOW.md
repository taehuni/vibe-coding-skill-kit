# README 확인부터 제출까지

목적은 실제 과제를 이해하고, 허용된 환경에서 핵심 기능이 동작하는 결과물을 만든 뒤, 본인이 구현을 설명할 수 있는 상태로 제출하는 것이다. 특정 예시 서비스의 완성 코드를 미리 준비하는 과정이 아니다.

## 1. 내가 README와 요구사항을 먼저 읽기

최상위 README, 별도 요구사항·평가 기준·제출 안내를 직접 읽는다. 프로젝트에 작업 지침 파일이 있으면 함께 확인한다.

- 누구의 어떤 문제를 해결하는지 한 문장으로 적는다.
- 필수 기능, 필수 입력·출력, 제출 경로, 실행 방법에 표시한다.
- 제공된 API·데이터·계정과 금지된 도구를 구분한다.

**끝나는 기준:** 과제 목적과 제출물을 내 말로 설명할 수 있다. 아직 스킬이나 큰 패키지를 설치하지 않는다.

## 2. AI에게 README·요구사항을 분석시키기

[첫 프롬프트](FIRST_PROMPT.md)를 사용한다. AI에게 구현부터 맡기지 말고, 요구사항과 실제 파일을 대조하도록 한다.

- 필수 / 선택 / 불명확 / 환경 제약을 구분한다.
- README에 명시된 내용과 AI의 추측을 구분한다.
- 각 필수 요구사항에 확인 방법을 붙인다.

**끝나는 기준:** 내가 읽은 내용과 AI의 해석 차이를 확인했고, 미확정 사항 목록이 있다.

## 3. 실행 환경 확인하기

프로젝트 구조, 언어·버전, 이미 설치된 패키지, 실행·테스트 명령, 제공된 자원을 확인한다. 환경변수는 이름과 설정 여부만 본다.

- 기존 프로젝트가 있으면 우선 기존 방식대로 실행한다.
- 내부 미리보기 연결 방식, 서버 주소·포트·경로를 확인한다.
- API, DB, 파일 저장, 마이크 등이 필요한지 요구사항과 대조한다.

플랫폼이 서버를 `0.0.0.0`에 열도록 안내한다면 그 조건과 실제 포트를 맞춘다. `3000` 같은 예시 포트를 무조건 고정하지 않고, 실행 중인 서버와 미리보기 주소가 일치하는지 확인한다.

**끝나는 기준:** 지금 실행할 수 있는 것과 추가 확인이 필요한 것을 구분했다. 플랫폼 설정은 건드리지 않는다.

## 4. 현업자에게 핵심 질문하기

과제에 제공된 현업자·고객 역할의 대화 채널이 있을 때 그 안에서 질문한다. 답변을 기다리면서 기존 파일 확인처럼 독립적으로 할 수 있는 작업은 진행한다.

우선 질문할 내용:

1. 사용자가 가장 자주 겪는 문제와 가장 중요한 사용 장면은 무엇인가요?
2. 이번 결과물에서 꼭 확인하고 싶은 기능 세 가지는 무엇인가요?
3. 어떤 결과를 보면 사용자가 도움을 받았다고 판단하나요?
4. 실제 사용 예시 하나와 바람직한 결과 예시를 설명해 주실 수 있나요?
5. 데이터 보관·개인정보·응답 시간·실패 상황에서 지켜야 할 조건이 있나요?

질문은 이미 README에 답이 있는 것부터 다시 묻지 않는다. 목적과 우선순위가 명확해지는 질문부터 묻는다. 환경·권한·API 제공 여부는 현업자 추측보다 README와 플랫폼의 공식 지원 채널에서 확인한다.

**끝나는 기준:** 답변으로 바뀐 요구사항을 정리하고, 답을 못 받은 부분은 가정이라고 명시했다.

## 5. 구현 범위와 완료 기준 정하기

필수 기능을 사용자의 한 흐름으로 묶고, 남는 기능은 후순위로 둔다.

- 최소 흐름: 입력 → 실제 처리 → 결과 표시 → 필요할 때 저장·재조회.
- 기능마다 성공·실패·빈 데이터의 동작을 정한다.
- 테스트와 직접 확인 중 어떤 방법으로 완료를 판정할지 정한다.

**끝나는 기준:** 무엇이 동작하면 제출 가능한지 합의되어 있다. 시간과 자원이 부족할 때 줄일 항목도 정해져 있다.

## 6. 기술·공개 스킬·라이브러리 선택하기

기존 프로젝트의 기술을 우선 사용한다. [스킬 목록](SKILLS.md)에서 현재 단계에 필요한 것만 고른다.

- 스킬은 AI의 작업 지침, 라이브러리는 서비스 코드의 기능이다.
- 공개 저장소의 일부 알고리즘·컴포넌트를 쓸 때는 출처와 라이선스를 남긴다.
- 전체 서비스를 교체하는 예제, 외부 AI 연결, 자동 화면 조작, 결과 업로드 기능은 가져오지 않는다.
- 라이브러리는 설치 가능성, 추가 실행 프로그램·모델 필요 여부, CPU·메모리, 외부 통신을 확인한다.

**끝나는 기준:** 추가하는 항목마다 과제에 필요한 이유와 허용 범위를 설명할 수 있다. 처음부터 10개를 모두 활성화하지 않는다.

## 7. 막힐 수 있는 핵심 조건부터 작게 검증하기

전체 화면을 만들기 전에, 실패하면 계획을 바꿔야 하는 요소를 하나씩 실제 환경에서 확인한다.

| 필요한 기능 | 먼저 확인할 것 |
| --- | --- |
| 서비스용 AI | 제공 API 여부, 허용 모델·기능·주소, 서버에서의 최소 요청 |
| 음성 입력 | 내부 미리보기의 마이크 권한, 실제 녹음 가능 여부, 녹음 형식 |
| 음성 분석 | 녹음 형식을 라이브러리가 읽는지, 변환 도구가 필요한지, 처리 시간 |
| DB | 실제 생성·저장·재조회, 서비스 재시작 뒤 유지 여부 |
| 파일 처리 | 허용된 입력 경로·형식·용량, 잘못된 파일 처리 |

위 항목은 해당 요구사항이 있을 때만 확인한다. 제공 API가 없다면 개인 키나 다른 AI로 우회하지 않는다. 음성 분석의 단순 지표를 검증 없이 심리 상태·긴장도의 확정 판정으로 표시하지 않는다.

**끝나는 기준:** 핵심 제약이 실제로 통과했거나, 미지원 사항과 요구사항을 어떻게 조정할지 확인했다.

## 8. 최소 사용 흐름을 처음부터 끝까지 연결하기

입력부터 결과까지 한 번은 실제로 통과하게 만든다. 가짜 성공 응답이나 임시 데이터 사용 여부는 명확히 구분한다.

- 화면, 서버, 필요한 DB·처리를 연결한다.
- 핵심 새 로직은 작은 테스트로 검증한다.
- 진행 중·성공·실패 상태를 사용자에게 보여 준다.

**끝나는 기준:** 직접 입력한 값이 실제 처리 결과로 나타난다. 저장이 필수면 저장한 결과를 다시 읽을 수 있다.

## 9. 필수 기능과 화면을 보완하기

최소 흐름 위에 빠진 필수 기능과 사용 편의를 더한다.

- 입력 검증, 재시도, 중복 실행 방지, 빈 상태를 처리한다.
- 버튼·안내 문구·간격·대비·키보드 접근을 점검한다.
- 선택 기능은 필수 흐름과 제출 시간을 해치지 않을 때만 추가한다.

**끝나는 기준:** 필수 요구사항별 구현 위치를 가리킬 수 있고, 주요 실패 상황에서도 서비스가 설명 가능한 상태를 보여 준다.

## 10. 테스트와 내부 미리보기에서 확인하기

제공된 터미널에서 테스트·빌드·형식 검사를 실행한다. 화면은 내부 미리보기에서 내가 직접 입력하고 확인한다. 브라우저 자동 조작·자동 캡처로 대체하지 않는다.

- 처음 사용자 흐름, 잘못된 입력, 새로고침, 재조회 등 해당 기능의 주요 경우를 확인한다.
- 키가 화면·로그·소스에 노출되지 않았는지 점검한다.
- 실제 실행 결과에 따라 통과·실패·미확인을 구분한다.

**끝나는 기준:** 검사 명령과 실제 결과, 직접 확인한 범위, 남은 한계가 정리됐다.

## 11. 실행 설명과 제출 준비하기

실제 명령으로 다시 실행할 수 있도록 문서를 정리하고, 본인이 구조를 이해했는지 확인한다.

- 실행 방법, 필요한 환경변수의 이름, 데이터 저장 위치를 적는다.
- 주요 구현, 선택 이유, 사용한 공개 자료, 미완성·제약을 적는다.
- 필수 파일 경로와 저장 상태를 확인한다. 마지막 순간까지 기능을 늘리지 않는다.

**끝나는 기준:** 다른 사람이 문서대로 실행할 수 있고, 내가 핵심 구현과 한계를 직접 설명할 수 있다.

## 12. 제출하고 접수 상태 확인하기

당일 안내가 정한 여유 시간을 확보해 플랫폼 안에서 제출한다. 파일 저장이나 버전 기록이 최종 제출을 대신한다고 가정하지 않는다.

- 필수 제출물을 확인하고 지정된 제출 절차를 진행한다.
- 접수·확정·최종 완료가 구분돼 있다면 화면 안내에 따라 각 상태를 확인한다.
- 후속 문답이 있으면 해당 규정에 따라 본인이 직접 답변하고 종료 상태를 확인한다.

**끝나는 기준:** 플랫폼에서 최종 완료 상태를 확인했다. 금지된 외부 백업·Push·캡처를 하지 않는다.
